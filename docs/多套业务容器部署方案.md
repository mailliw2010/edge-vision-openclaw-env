# 多套业务容器部署方案

## 1. 目标

本方案用于同一台服务器节点上部署多套业务容器，满足以下需求：

- 每位开发人员有独立的一套业务运行环境
- 开发完成后统一通过 `fork + MR` 合并到主仓库
- 主环境由你统一审核和合并
- 多套环境之间尽量互不影响，且便于维护、排障和回滚

结合当前仓库现状，推荐采用：

- `bridge` 网络作为主部署方式
- `fork + MR` 作为 Git 协作方式
- middleware 可以共享，但必须做逻辑隔离

---

## 2. Git 协作流程

### 2.1 推荐模式：Fork 协作

建议把主业务仓库作为“上游仓库”，每位开发人员从主仓库 `fork` 一份自己的仓库。

流程如下：

1. 你维护主仓库，作为唯一权威代码来源
2. 开发人员从主仓库 fork 出自己的仓库
3. 开发人员在自己的 fork 仓库中建分支开发
4. 开发完成后向你的主仓库发起 MR
5. 你在主仓库统一 review、测试、合并

### 2.2 这种方式的好处

- 开发人员不会直接污染主仓库
- 每个人有自己的远程仓库，权限边界更清晰
- 适合多人并行开发
- 便于控制提交节奏和合并节奏

### 2.3 前提条件

`fork + MR` 不是纯 Git 本地能力，通常需要：

- GitLab
- Gitea
- Forgejo
- 或其他支持 fork / MR 的代码托管平台

如果只是一个裸 Git 仓库，则只能退化为“分支 + MR”模式，不能真正 fork。

---

## 3. 网络方案

### 3.1 选择 `bridge` 的原因

对于当前场景，`bridge` 是推荐的主方案：

- 改动小
- 符合现有 compose 写法
- 端口映射清晰
- 容器间联调方便
- 便于复制出多套开发环境

---

## 4. 共享 middleware 会不会共享数据

会。这个问题必须单独说明。

如果多个业务系统共用同一套 middleware 实例，并且使用同样的数据库名、bucket、vhost、Redis DB、流名称，那么**数据默认就是共享的**。

### 4.1 在当前仓库里，容易共享的数据点

#### PostgreSQL

如果多个环境连接同一个数据库 `openclaw`，那么表数据会直接共享。

#### MinIO

如果多个环境使用同一个 bucket，上传的对象会互相可见。

#### RabbitMQ

如果多个环境使用同一个 vhost，消息队列、交换机、队列名会互相影响。

#### Redis

如果多个环境使用同一个 DB index，并且 key 前缀不隔离，缓存和状态会串。

#### ZLMediaKit

如果流名、配置或回调不隔离，媒体流也可能互相看到。

### 4.2 结论

- **共享 middleware 不等于一定共享数据**
- 但如果不做额外隔离，默认就是共享数据
- 对多人并行开发来说，这种默认共享是有风险的

---

## 5. 推荐架构

建议采用三层结构：

### 5.1 主业务环境

主环境用于：

- 接收合并后的主分支代码
- 做统一联调和回归
- 作为最终验证基线

### 5.2 开发业务环境

每位开发人员一套独立业务容器，建议做到：

- 独立 Compose project
- 独立端口段
- 独立工作目录
- 独立配置目录

### 5.3 middleware 层

middleware 有两种做法：

1. 共享一套 middleware，但按环境做逻辑隔离
2. 每位开发人员独立一套 middleware

推荐顺序是：

- 先做共享 middleware + 逻辑隔离
- 如果后续发现串数据或隔离压力大，再拆成独立 middleware

---

## 6. 共享 middleware 的最小隔离方案

如果你想在改动最小的情况下共享 middleware，建议至少做到下面这些隔离。

### 6.1 PostgreSQL 隔离

推荐方案：

- 每个开发环境一个 database
- 或每个开发环境一个 schema + 一个独立用户

建议命名：

- `openclaw_alice`
- `openclaw_bob`
- `openclaw_charlie`

最低要求：

- 不同环境不能共用同一个 database
- 不同环境使用不同账号

### 6.2 MinIO 隔离

推荐方案：

- 每个开发环境独立 bucket
- 或 bucket 前缀隔离

建议命名：

- `openclaw-alice`
- `openclaw-bob`
- `openclaw-charlie`

最低要求：

- 不同环境不要写同一个 bucket
- bucket 权限和访问凭证最好分开

### 6.3 RabbitMQ 隔离

推荐方案：

- 每个开发环境一个 vhost
- 每个环境独立账号

建议命名：

- `/openclaw-alice`
- `/openclaw-bob`
- `/openclaw-charlie`

最低要求：

- 不同环境不要共用同一个 vhost
- exchange / queue / routing key 要按环境加前缀

### 6.4 Redis 隔离

推荐方案：

- 每个开发环境一个 DB index
- 再叠加 key 前缀隔离

建议命名：

- `0` 给主环境
- `1` 给 alice
- `2` 给 bob
- `3` 给 charlie

最低要求：

- 不同环境不要使用同一个 Redis DB index
- 所有 key 必须带环境前缀，例如 `alice:session:*`

### 6.5 ZLMediaKit 隔离

推荐方案：

- 每个开发环境独立端口段
- 每个环境独立配置文件
- 流名加环境前缀

最低要求：

- 不同环境不能共用同一组媒体端口
- RTMP / HTTP / RTSP / SRT 端口要分开
- 回调地址不能写死 `127.0.0.1`，要改成环境可达地址

## 7. 现有 compose 需要改多少

基于你当前仓库，采用 `bridge + 共享 middleware + 逻辑隔离` 时，改动量是可控的。

### 7.1 业务 compose

主要是 [compose.openclaw.yml](../compose.openclaw.yml)

需要做的事：

- 为每个开发环境分配一套端口
- 通过 `.env` 区分不同开发人员
- 保持 `bridge` 和现有网络结构不变

这个文件本身不需要大改，更多是参数化。

### 7.2 middleware compose

主要是 [middleware/compose.openclaw.middleware.yml](../middleware/compose.openclaw.middleware.yml)

需要做的事：

- 保留一套共享 middleware，或者按需拆成多套
- 给 PostgreSQL / MinIO / RabbitMQ / Redis / ZLMediaKit 加上环境隔离参数
- 对 MinIO、RabbitMQ、Redis 做环境级别的命名隔离

### 7.3 根环境文件

主要是 [`.env`](../.env)

这里是唯一的环境文件，也是控制平面和业务层的单一事实源。现在
根 `.env` 按三类分组：

- 标准类型：`LANG`、`TZ`、`HTTP_PROXY`、`http_proxy`、`NO_PROXY` 等
- 业务类型：`OPENCLAW_IMAGE`、`OPENCLAW_GATEWAY_TOKEN`、挂载目录、业务端口
- 中间件类型：`OPENCLAW_POSTGRES_*`、`OPENCLAW_MINIO_*`、`OPENCLAW_RABBITMQ_*`、`OPENCLAW_ZLM_*`

控制平面通过 `docker compose --env-file ./.env` 注入环境变量，宿主机
总入口 [`bootstrap-startup.sh`](../bootstrap-startup.sh) 也会先加载同一
份 `.env`，再执行 middleware 初始化脚本
[`init-phase1-middleware.sh`](../init-phase1-middleware.sh)。

### 7.4 MinIO 配置

主要是 `.env` 里的 `OPENCLAW_MINIO_*`，以及
[`middleware/compose.openclaw.middleware.yml`](../middleware/compose.openclaw.middleware.yml)
对 MinIO 容器的显式环境变量映射。

当前这里写死了：

- `MINIO_BROWSER_REDIRECT_URL=http://127.0.0.1:9011`

如果共享 middleware 或多环境部署，这个地址必须改成对应环境的可访问地址。

### 7.5 其他文件

还需要检查：

- [middleware/zlmediakit/config.ini](../middleware/zlmediakit/config.ini)
- [README.md](../README.md)
- [middleware/README.md](../middleware/README.md)
- [`bootstrap-startup.sh`](../bootstrap-startup.sh)
- [`init-phase1-middleware.sh`](../init-phase1-middleware.sh)

这些文档里目前还写着共享网络和 localhost 端口，后续需要同步更新。

## 8. 最小可落地方案

如果目标是“尽快能用，且尽量少改”，我建议这样落地：

1. 业务层继续使用 `bridge`
2. 每位开发人员一套独立 `.env`
3. 每位开发人员一组固定端口
4. middleware 先共享一套
5. middleware 的数据库、bucket、vhost、Redis DB 全部按环境隔离
6. ZLMediaKit 端口和流名按环境前缀区分
7. Git 采用 `fork + MR`

这套方案的核心是：

- 网络改动小
- 协作方式清晰
- 数据隔离可控

## 9. 风险和边界

### 9.1 共享 middleware 的风险

如果隔离没做好，最常见的问题是：

- 某个开发环境误删别人的数据
- 缓存串写
- 消息队列串写
- MinIO 对象混在一起
- 媒体流互相影响

### 9.2 什么时候不建议共享 middleware

下面这些场景建议独立 middleware：

- 开发人员之间不能互相看到数据
- 需要做破坏性测试
- 需要长时间保留各自环境
- 业务对隔离要求非常高

### 9.3 什么时候可以共享 middleware

下面这些场景共享 middleware 是可接受的：

- 只是做日常功能开发
- 数据量不大
- 环境之间的隔离策略明确
- 你能接受统一维护中间件

---

## 10. 结论

当前最合理的方案是：

- `bridge` 作为主网络方案
- `fork + MR` 作为 Git 协作方式
- middleware 可以共享，但必须做逻辑隔离
- PostgreSQL、MinIO、RabbitMQ、Redis、ZLMediaKit 都要有环境级隔离策略

这样做的好处是：

- 改动最小
- 可维护性更高
- 多人协作更清晰
- 后续如果要升级成独立 middleware，也有平滑演进路径
